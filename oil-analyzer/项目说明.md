给**要改这份代码的人**看。所有 `oil_monitor_gui.py:行号` 基于当前版本实测 **5042 行**（UTF-8 无 BOM、CRLF）；README 里写的"约 2800 行 / 启动.bat"已过期。

## 1. 这是什么

一句话：**单文件 tkinter 桌面工具**，把现场导出的油液监测数据（Excel / CSV / 多层 zip）扫成一张统一记录表，做阈值判定与趋势图，再批量产出「月度磨粒分析 Excel + 油品分析 Word 报告」。

面向谁、解决什么：

- 用户是油液监测/诊断工程师（报告固定署名：`oil_monitor_gui.py:1878-1880`，珠海市鑫世达测控技术有限公司 / 曹居易 / 王振尧）。
- 痛点：数据散在多层目录与压缩包里、表头写法五花八门、每月每台机组要手工套模板出报告。程序把「识别 → 入库 → 筛选 → 判定 → 出报告」做成流水线。
- 三个使用面：① GUI 浏览/筛选/趋势；② 工具栏「报告」按时间段批量出 Excel+Word；③ `磨损分析.py` 命令行批处理（无界面）。

## 2. 快速运行

依赖（`requirements.txt`，三项都必需）：`openpyxl>=3.1`、`python-docx>=1.1`、`matplotlib>=3.7`；tkinter 随 Windows 官方 Python 自带。

```bash
pip install -r requirements.txt
```

三种启动：

| 方式 | 入口 | 行为 |
| --- | --- | --- |
| bat | 双击 `OilLab.bat` | `chcp 65001` → 按 `本地pythonw.exe` → `pythonw` → `pyw -3` → `python` → `py -3` 逐级回退，`start ""` 后台起 |
| vbs | 双击 `OilLab.vbs` | 同样的回退链，全失败弹 MsgBox；`sh.Run ..., 0, False` 不显示控制台 |
| 命令行 | `python oil_monitor_gui.py` | 直接跑 GUI；`hide_console()`（`oil_monitor_gui.py:3370`）只有在控制台仅挂本进程时才隐藏，在终端/VSCode 里运行会保留窗口 |

批处理（无 GUI）：

```

python oil_monitor_gui.py --wear "D:\油液数据" "D:\输出" 2026-09-01 2026-09-30
```

两者最终都进 `run_wear_cli`（`oil_monitor_gui.py:4957`）；`磨损分析.py` 只是它的一层交互壳（`磨损分析.py:20`）。

## 4. 数据约定

### 目录结构

```
<顶层目录>\
├─ 华能电厂 #1 汽轮机\           ← 项目（一级子文件夹）
│  ├─ 2026-09 取样\             ← 任意层级文件夹
│  │  ├─ 磨损\磨损.csv
│  │  └─ 水分\水分.csv
│  └─ 2026-10.zip               ← 压缩包，可嵌套（≤4 层）
└─ 营盘梁.zip                    ← 根目录的 zip 自己就是一个项目
```

- 项目名 = 一级子文件夹名；根目录散文件归入 `project_label(main_dir)`（`oil_monitor_gui.py:546`，"油液/数据"这类通用名会再向上取一级）。
- 根目录 zip 以包名当项目（`oil_monitor_gui.py:1384-1385`）。
- 若根目录**≥2 个**"像机组"的包/夹（`#1`、`26#`、`H01-6.25MW`…，1370-1375）→ 整个目录算一个项目，`collect_units`(1408) 用总包名作项目名、按机组号合并，`home`/`excel` 之类中间层在树里被压平。
- 虚拟路径 `vpath` 用 `/` 分隔：`项目/子目录/file.xlsx`、`营盘梁.zip/youye_#4.zip/home/excel/清洁度.csv`。树 iid 用 `::` 拼接（项目名含 `::` 会解析错，属边界情况）。

### 文件名解析规则

- `guess_device`(599)：从 vpath 各段**从后往前**找 `#N` 或 `N#`（`UNIT_PATTERN`，574）→ 显示成 `N#`；其次 `looks_like_unit_name`（`WTG01`/`H01-6.25MW`）；再退回 `clean_device(文件名)`（去日期、去掉"光谱/磨损/检测/汇总"等通用词，565-571）；全失败 → `"未标注设备"`。
- `guess_date`(626)：`DATE_IN_NAME`(464) 在**整条 vpath** 上抓第一个 20xx 年月日。
- 表内日期优先于文件名：`parse_workbook`(1121) 先把 `{"device","date"}` 作为 `meta_extra` 传入，表头/表头上方识别到的值会覆盖。

### 支持的文件类型

- `EXCEL_EXT = {".xlsx", ".xlsm", ".xls", ".csv"}`（156）。**`.xls` 是假支持**：`load_sheets` 直接 `raise ValueError("旧版 .xls 需另存为 .xlsx")`（661-662），该文件在树里显示为红色 error。
- CSV 编码尝试顺序：`utf-8-sig → gb18030 → utf-16`（649）；磨粒 CSV 是 `utf-8-sig → gbk → utf-8`（1601）。
- 压缩包只支持 `.zip`；`fix_zip_name`(1511) 修 GBK 文件名；跳过 `__MACOSX`、`~$*`、`._*`（1480-1484）。
- 表格版式不用管，`parse_sheet`(793) 自动挑：宽表 `parse_matrix`(808) / 长表 `parse_long`(876，需要"参数+结果"两列) / 横向表 `parse_transposed`(918) / 单参数 `parse_fallback`(937)；30 行以上、带时分秒"时间"列的 CSV 走在线传感器分支 `parse_sensor_series`(1015)。

### `PARAMS` / `META_KEYS` 含义

每个参数一条：`key`（英文键，如 `wear_Fe`、`clean_nas`、`water_pct`、`vis_40`）、`name`（展示名 `铁(Fe)`）、`group`（7 组之一）、`unit`、`aliases`（表头别名）、`direction`（`"max"` 越大越差 / `"min"` 越小越差 / `None` 不判定）、`warn`、`alert`。

- 23 个磨损元素由 `_WEAR`(222-238) 批量注册，`warn = 0.7 × alert`；`Ca/Mg/Zn/P/Mo/B/Ba` 无上限 → `direction=None` → `judge` 恒返回「待定」。
- **磨粒浓度 `wear_ferrous` / `wear_nonferrous`**（:250-258）是后加的：单位 `mg/kg`，阈值直接取 `REPORT_LIMITS`（铁磁 20/25、非铁磁 15/20），别名含 `铁磁磨粒`、`B7`、`G7` 等。这样界面与报告共用同一套磨粒阈值，CSV 里出现对应列也能自动识别判定。
- 别名索引 `_ALIAS_INDEX` 在 280-282 一次性建立，`identify_param`(295) 只查这张表 + 一串中文关键词兜底（304-347）。
- `META_KEYS`(284) 是 5 类列名别名（device/point/oil/date/sample_no），只在**表头上方 30 行**（`meta_from_rows`，limit=30）里按「`标签：值`」或「标签右侧 1~2 格」识别（686-711）。
- 在线监测里不认识的通道动态注册为 `sensor_<md5[:8]>`（979-985），`direction=None` 永不判定；下次启动由 `_load_dynamic_params`(3915) 从库里回填名称/单位。
- `thresholds.json` 按 `key` 覆盖 `warn/alert/direction`，重扫后生效（385-410）。

## 5. 报告生成链路

### A. 磨损 Excel（真·模板驱动）

1. `export_wear`(4825)：要求左侧已选项目 → 取该项目所有 `is_wear_csv` 文件（`.endsWith("磨损.csv"/"mosun.csv")` 或文件名以 `oil` 开头，559-562）。
2. 模板 `wear_template_path`(1595) → `templates/磨损分析模板.xlsx`，打包后走 `sys._MEIPASS`。
3. `PeriodDialog`(3833) 默认时间段 = 全部磨损 CSV 的首末日期（4857-4874）。
4. 逐文件 `load_wear_csv`(1599)（第 1 列时间 + 10 个"…微米范围微粒数"列，缺列则退回第 2~11 列 1611-1614）→ `filter_rows_by_window`(3815) → `analyze_wear`(1642)。
5. `build_wear_workbook`(1793)：
   - `load_workbook(template)` 打开副本；`ws.delete_rows(last_row+1, …)` 删掉模板预置的 7732 行（模板实测 `原始数据粘贴区` max_row=7732）；
   - 整块覆盖写 A1…K{n}（含表头行）；M…V 写 `=B3-B2` 增量公式（1816-1819）；
   - `月度分析表格`：B3:K3 改成 `=原始数据粘贴区!X{末行}-…X2`，B4:K4 `=INT(X3/天数)`，B6:K6 浓度公式里模板的 `28` 换成实际采集天数（1821-1831）；
   - B7/G7 数字格式 `0.00E+00`、B8 写结论、B8:L8 按结论上色（正常 `AACC99` / 预警 `FFFF99` / 报警 `FFC7CE`，1696-1722、1832-1839）；
   - `_rebuild_wear_charts`(1773)：`sh._charts = []` 清空后按 5×2 锚点 `A1/L1 … A41/L41` 重建 20 张 `openpyxl LineChart`（每通道"累计+增量"各一张）。
6. `build_wear_summary`(1847) → `机组磨损数值汇总.xlsx`（机组号/年月/B7/G7/结论）。

口径（`analyze_wear`）：先删全 0 行 → 单调递增修复（`max(当前, 上一行)`）→ `颗粒数=末-首`；`个/天=INT(颗粒数/采集天数)`；`个/L=个/天/(75×1440)`；`浓度=(7.87/0.86)×1e9×球体积(40μm)×颗粒数 ÷ (π×7mm²×0.64m/s×86400×天数)`；`B7=浓度[0:5]` 求和、`G7=浓度[5:10]` 求和，极小值抬到 0.01。**Python 算一遍写结论，公式另写一遍进 xlsx，两边口径必须手动保持一致。**

### B. Word 分析报告（**从零生成，不用任何 docx 模板**）

`build_analysis_report_docx`(2619-3023)：

1. 数据：`collect_report_metrics`(2006) **只读原始 CSV**（不读数据库记录）——`_find_unit_file`(1936) 按文件名关键词找 `磨损/mosun`、`水分/shuifen`、`清洁度/qingjiedu`、`粘度/niandu`（别名表 1937-1938，`Oil…csv` 视为磨损+水分的合并文件 1949-1951），再用写死的列名取数：`水分传感器湿度`、`水分传感器PPM`、`NAS5-15`、`粘度VT40`（2026-2039）。磨损走 `load_wear_csv`+`analyze_wear`。
2. `Document()` → `sec.page_width/height` A4、四边 1.8cm、`Normal` 字体微软雅黑 10.5pt 且设 `w:eastAsia`（2665-2675）。

## 6. 已知坑与注意点

1. **README 与代码已脱节**：实际 5042 行（不是 2800）；README 说的 `启动.bat`/`启动.vbs` 实际叫 `OilLab.bat`/`OilLab.vbs`；README 说宾泉报告用 `templates/宾泉_月度报告模板.docx`，实际是代码从零拼 docx。
2. **编码**：源码/README/bat/vbs/spec/requirements **全部 UTF-8 无 BOM**（字节级确认）。但 PowerShell 5.1 `Get-Content` 默认按 GBK 解码，直接看会全是乱码——别以为文件坏了，用 `Get-Content -Encoding UTF8` 或编辑器按 UTF-8 打开。`OilLab.bat` 里 `chcp 65001` 与 UTF-8 正文配套，但 cmd "先切码页再解析后续行"的行为在不同 Windows 版本上不完全一致（推断：老系统上 `echo` 中文仍可能花屏，不影响启动逻辑）。
3. **限值分两类，不是冲突（此前本文件写错过，已更正）**：`PARAMS`（:232 起，`judge` :413 使用）是元素/理化指标，`wear_Fe` 是 **ppm**（warn 84 / alert 120）；`REPORT_LIMITS`（:1907，`_judge_max` :1978 使用）是 **磨粒浓度 mg/kg**（铁磁 20/25、非铁磁 15/20）。两者物理量不同，本来就该分开。
   - 真正的问题是**同一套磨粒阈值写了两遍**：`analyze_wear` 的结论分支里是字面量 `20/25/15/20`（原 1709/1712/1716），改 `REPORT_LIMITS` 会导致"同一份报告里表格判定与结论文字不一致"。
   - 已抽取 `wear_verdict()`（:1642-1657）统一从 `REPORT_LIMITS` 取值，`analyze_wear` 不再含阈值字面量；`tests/test_wear_limits.py` 以旧逻辑为参照做了 5041 点网格等价性验证（判定零变化）。
4. **报告指标只认原始 CSV**：项目里只有 Excel 化验单时，Word 报告会写"本期未采集到水分/清洁度/粘度数据"，哪怕界面表格里这些参数都有（`_find_unit_file` 只匹配 `.csv`，1944）。列名还是写死的四个中文表头，现场导出改名就全空。
5. **【已修】时间格式曾经静默丢行**：旧 `parse_datetime_text` / `_wear_time` 只认零填充格式（`%Y-%m-%d %H:%M:%S` 等），`2026/9/5 8:05` 被判无效直接丢；丢光后 `days` 回落 `WEAR_PERIOD_DAYS=28`，浓度口径随之变。
   - 现在：`_wear_time` 只是 `parse_datetime_text` 的别名（原先是一份少认 `%Y/%m/%d` 的副本）；解析器新增正则兜底，支持 `2026/9/5 8:05`、`2026.9.5`、`2026年9月5日`、ISO `T` 分隔、带小数秒。
   - 失败不再静默：`PARSE_STATS["unparsed"]` 计数，扫描结束时状态栏追加"N 处时间文本无法解析"；`analyze_wear` 返回 `days_estimated` 标记是否用了 28 天兜底。
   - 回归测试 `tests/test_time_parse.py`（24 项）。
6. **【已改】机组台数改为配置驱动**：原先写死 `_declared = 75 if ("营盘梁" in project or "岱海" in project) else 0`，项目名改一个字就失效。
   - 现在 `report_unit_count()`（`oil_monitor_gui.py:2619-2664`）优先读 `templates/*_报告配置.json` 的 `unit_count`，无配置才回落到历史规则（营盘梁/岱海=75）。匹配方式：`project` 字段互相包含，或文件名前缀（`营盘梁_报告配置.json`）出现在项目名里。
   - 读取用 `utf-8-sig` 容忍 BOM，坏 JSON 跳过不影响其它配置。回归测试 `tests/test_report_config.py`（17 项断言）。
   - **注意**：`missing_unit_text`、`sections`、`history` 三个字段目前仍未被使用（缺失文案还写死在 2271/2384/2845/2933），接线需要确认文案口径后再做。
7. **历史浓度不是放 xlsx 就生效**：宾泉走 `BINQUAN_HISTORY`(44-64)、营盘梁走 `YINGPAN_HISTORY`(72-146)，都在 py 里硬编码；只有"旺海装/汪海庄"才读 `templates/旺海装_历史浓度.xlsx`（2590-2616、2947）。`templates/宾泉_历史浓度.xlsx`、`营盘梁_历史浓度.xlsx`、`*_月度报告模板.docx`、`*_报告配置.json` **代码里全无引用**（grep 无命中），属于参考资料，改了不会影响输出。
8. **Excel 合并单元格**：模板「月度分析表格」有 `A1:L1`、`B7:F7`、`G7:K7`、`B8:L8` 四处合并；代码只写锚点（`wa["B7"]`、`wa["G7"]`、`wa["B8"]`）。改版式时若把锚点挪到非左上角单元格，写入会抛只读错误（推断，openpyxl 的 `MergedCell` 行为）。
9. **公式不算值**：B3/B7/G7 等都是字符串公式，openpyxl 不计算；用 `data_only=True` 读回是 `None`，必须 Excel/WPS 打开一次才有数——所以"生成后自检数值"必须用公式口径在 Python 里另算一遍。
10. **图表依赖 openpyxl 私有 API**：`sh._charts = []`(1784) 和 `chart.series[0].val.numRef.f`(1767) 都不是公开接口，升 openpyxl 大版本可能失效（**未确认**：本机只有 openpyxl 3.1.5 且只做了读取验证，matplotlib 未安装，写图未实测）。
11. **`.xls` 假支持**：`EXCEL_EXT` 收了 `.xls`，`load_sheets` 直接报错（661-662），树里是红色 error 节点，`files.status='error'`，明细里记录数 0。
12. **默认筛选藏数据**：状态默认「异常/关注」（3954、4106）+ `clean_iso` 行永远不进表（4436）→ 刚导入常看到空表。只有"扫完仍为空"才自动切「全部」（4726-4730）。
13. **一切锚在程序目录**：换机器/换目录就"丢现场"（`main_dir` 存在 `gui_state.json`，但缓存按 vpath 存在 exe 旁的 `oil_cache.db`）。程序目录只读则 DB/状态写不进去。
14. **单实例**：`CreateMutexW("OilLab_SingleInstance")` + `FindWindowW` **精确匹配窗口标题** `"OilLab · 油液监测报告工具"`（3346-3350）。改标题会让第二次启动不聚焦、直接静默退出。
15. **两处 SQLite 连接并发**：GUI 的 `self.store`(3881) 与 `Scanner.store`(1359) 各开一条连接，`timeout=15`（1174）；长扫描时界面查询可能短暂阻塞（推断）。
16. **环境坑**：本机 PATH 上的 `python.exe` 是 Microsoft Store 占位程序（`where python` → `WindowsApps\python.exe`，`python --version` 无输出），直接敲命令不会有任何反应，要用真装了依赖的解释器（推断：这正是 bat/vbs 逐级回退的原因）。
17. **`DB_SCHEMA_VERSION = 3` 是死常量**（41，全文件仅此一处）；真正触发"规则升级→全量重解析"的是 `PARSE_VERSION`(42) 与 `Scanner.run` 的比对（1533-1534）。改了 `PARSE_VERSION` 后，首次启动会重建全部记录（`force=True`）。
18. **扫描是追加的**：只删除"本次扫描到的项目"里消失的文件（1540-1543），其他项目的缓存保留；多项目会同时在树里。想清空只能点「清空缓存」。
