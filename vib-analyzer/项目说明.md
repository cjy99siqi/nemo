## 1. 这是什么

风电机组振动数据分析桌面工具：tkinter 单文件 GUI，批量读采集器导出的单通道 CSV，算特征指标入库做趋势，在谱图上标轴承/齿轮特征频率，最后套 Word 模板出月度报告。

- **输入**：CSV（无表头、单列加速度，`pd.read_csv(header=None).iloc[:,0]` `:826`），元数据全在**文件名**里（§4）；报告模板 `.docx`（默认 `数据\模板\田家寨项目报告模板.docx`）。
- **输出**：`vib_cache.db`（指标库）、`诊断关注清单.xlsx`、`输出\分析报告_<项目>_<起>_<止>_<戳>.docx`（`:5598`）。
- **不联网、无服务端**；一次运行 = 一个 tkinter 进程（`if __name__ == "__main__"` `:8234-8238`）。

### 3.5 齿轮啮合频率标记与判读
齿轮级在 `数据\机型库.json` 的 `gears`：`name / teeth / shaft / sideband`，可选 `gcd`（齿数公约数）与 `planets`（行星轮个数）。

| 项 | 说明 |
|---|---|
| `_gear_marks_for` | `mesh = teeth × 该轴转频`，画啮合谐波 + 边带。`spacing` 三档：`shaft`（±k×轴转频，色 `GEAR_SB_COLOR`）、`gcd`（GMF÷gcd 族，色 `GEAR_GCD_COLOR`）、`both`（默认） |
| 行星级 | 有 `planets` 时额外画「N×太阳轮自转」（色 `GEAR_PLANET_COLOR`）与「GMF÷行星轮数」 |
| `_gear_dialog` | 右键「齿轮频率…」：选机型/齿轮级/转速/啮合谐波/边带阶数/**边带依据**（轴转频 / GMF÷公约数 / 两者）。**只在 `齿轮箱` 测点显示**（`_is_gear_point :3612`；发电机/主轴承上看到的 GMF 是从箱体传过去的，不给入口） |
| `_draw_gear_marks` / `_draw_bearing_marks` | 画虚线 + **频率处横排标签**（`rotation=0`，`ha="center"`；`_label_row`/`_label_half` 按字数估宽、最多 3 行错开防重叠）。`_post_draw` 在有标注时把 top 留到 0.88（12% 窄带） |
| `gear_sideband_verdict` | **不是**取“相邻峰间隔中位数”（谱线密时会被噪声带跑，出现 `0.98Hz ≈ GMF/2` 这种鬼话）。做法：① 先把中心吸附到理论 GMF ±1.5% 内最强的峰（文件名转速是整数、齿数是标称，实际常偏 1–2%）；② 对每个候选间隔，检查 GMF ±k×间隔处**是否真的有点**，容差按谱线宽收口且不跨阶；③ 至少 2 处命中才算，只有一侧命中时给「≈N×某转频（仅一侧）」提示 |
| `_gear_diag_block` | 渲染右上角「齿轮判读」卡，3–5 行：`GMF / 边带≈命中项 / 指向 / 边带·主峰 严重度`。**不写齿轮级名**（级次在对话框里已选） |

判读规则与 18 个案例的出处见 **`齿轮啮合图谱经验.md`**（§3 边带间隔定位、§4 形态严重度、§7 行星级专有规则）。
回归测试：`tests\test_gear_sideband.py`（合成 GMF/3 族与轴转频族，验证识别与匹配）。

### 3.5.1 故障模式判定（频谱形态 → 疑似故障类型）
把现场「频谱形态 → 故障类型」的判据做成可执行规则，输出**疑似 + 依据**，不做硬结论。

| 组件 | 说明 |
|---|---|
| `FAULT_MODE_T` | 阈值表（1X 占比、谐波门槛、边带密度、峭度、轴承倍率…），现场跑一轮再微调 |
| `spectrum_evidence(f, amp, machine, f_rot, sig)` | 一次算齐证据：最明显齿轮级的谐波族（**净峰高**＝峰－邻域中位）、边带命中间隔/数量/比值、H/M/S/L 里 1X 最突出那根轴的 1X/2X/0.5X、高频本底、轴承阶次峰（≥60Hz 且避开齿轮谱线）、时域峭度/峰值因子 |
| `fault_modes(ev, point)` | 11 类规则逐一匹配；每条有**核心证据**（核心不成立直接跳过）、可选**一票否决**；置信度＝成立条数/总条数，≥60% 才输出；同分按 `FAULT_MODE_SEV` 严重度排序 |
| 出口 | 谱图卡末两行「疑似 X 67%」「依据 …」；报告 `report_gear_label` 末尾追加「；疑似 X（67%）」 |

覆盖的 11 类：不平衡、轴弯曲、均匀磨损、齿廓偏差、齿根裂纹、齿崩损、断齿、侧隙过大、杂质异物、润滑不良、齿轮箱轴承损伤。

**两条重要边界**（实测踩出来的）：
- **不平衡/轴弯曲默认不输出**：单条频谱判不了（发电机 1X 本来就主导，40 条真实记录里 16 条会“命中”），要等趋势基线（同测点 1X/2X 随时间的增长）。代码保留在 `if is_shaft_pt and False:` 里。
- **模式按测点门控**：齿轮类（含 `齿轮箱轴承损伤`）**只认 `齿轮箱` 测点**。主轴承/主轴/发电机上看到的 GMF 是从箱体传过去的，在那儿判齿面故障没有物理依据（这几类测点走轴承/转子的判据），否则“齿轮箱轴承损伤”会满天飞。
- 实测：府谷 2026-06 的 40 条记录，30 条不出结论，其余是磨损 4 / 轴承 3 / 侧隙 2 / 裂纹 1。

- 标注存档按 **“测点 + 记录时间”** 存（`_point_key` 末尾拼采集时间）：同一测点切换数据时，不会把上一份数据的基频/标线带过来；只有回到同一条记录才恢复它的标注。

## 4. 数据约定

### 4.1 文件名（元数据唯一来源）
标准式（`parse_filename :539`）：
```
<项目>_<机组>_<测点>_<采样率>Hz_<时长>s_加速度值_[<rpm>_]<14位时间戳>.csv
例：田家寨_101#_主轴承_前轴径向_20000Hz_10.00s_加速度值_1483_20250504090029.csv
```
- `加速度值` 是**字面量**，不是占位符；时长可为小数（`[\d\.]+`）；速率必须是整数 `\d+Hz`。
- 有/无 rpm 两分支；**时间戳必须正好 14 位**，多一段后缀（如 `_1`）即解析失败→该文件被静默跳过（`process_one_csv` 返回“测点名为空”）。
- 五峰式另两套：`<项目>_<机组>_<测点>_<fs>Hz_加速度_<rpm>_<14位>` / 无 rpm 版（`:510-538`）。
- 项目/机组段**不能含下划线**（`pre_str.split("_", 2)`，测点段可以含）。
- zip 导入会按规范格式**改名落地**（`:7002-7010`），时长按 `行数/fs` 反算（`:.2f`），故时间戳目录 `sub = target/<14位戳>`。

### 4.2 测点清单
`rule_text :187-202` 定义 11 个规范名（阈值/滤波带）：`主轴承_前轴径向`、`主轴承_后轴径向`、`主轴_前轴径向`、`主轴_后轴径向`、`齿轮箱_一级内齿圈径向`、`齿轮箱_中部径向`、`齿轮箱_高速轴径向`、`齿轮箱_高速轴轴向`、`发电机_前轴承径向`、`发电机_前轴承轴向`、`发电机_后轴承径向`。
`default_bp_text :205-226` 另补 11 个别名（`齿轮箱高速轴`、`齿轮箱输入端`、`齿轮箱一级齿圈`、`发电机前轴`、`发电机后轴`、`主轴轴承`、`齿轮箱_二级齿圈径向` 等），`:234-236` 以阈值 0 并入 → **`rule_dict` 共 22 个可识别测点名**。
README 说的“9 个测点”是现场实际使用子集，不是代码上限。测点不在 `rule_dict` → 该 CSV 直接被拒（`:822`）。

### 4.3 机组编号映射
`report_unit_label :4983`：`101#~125# → 1#~25#`，**仅在项目名含“府谷”或“田家寨”时**才减 100；其它项目原样输出。五峰机组号不带 `#` 也能用（`rstrip("#号")` + `int`）。

### 4.4 目录约定
- 「上传」选的就是 `main_dir`；`vib_cache.db`、`项目档案.json`、`vib_annotations.json`、`诊断关注清单.xlsx` 都落在这里。

3. **汇总**：`report_stats(picked) :5004` → `agg[机组][测点] = {max, mean, n, ts, band, limit, ratio, grade, data_bad, peer_med}`。
   - `ratio = max / 第一限度`（`REPORT_VDI :4957`：低频 0.3、中频 7.5、高频 10.0）。
   - `report_grade :4969`：<80% 正常 / 80–100% 关注 / 100–200% 警告 / ≥200% 危险。
   - `vdi_only_normal`：主轴承/齿轮箱 `ratio≥0.8` 但无故障特征 → 改判“正常”（`:5038-5040`，`VDI_ONLY_PARTS :4955`）。
   - 数据异常：`max < 同型中位 × 0.05` → `data_bad`/“数据异常”（`DATA_BAD_RATIO :5062`）。
4. **故障判定（两条独立判据）**：
   - **轴承**：`report_scan_faults` 对每个测点看**最近 5 条**记录（`ENV_SCAN_FILES`）→ `report_env_peak` 做包络谱（`report_env_curve`，解调 1000–8000Hz、截 131072 点、汉宁窗）→ **按谐波族打分**（`bearing_family_match`：1× 必须落在 ±3% 内，2×…6× 逐阶去找，命中阶数越多、各阶偏差越一致分越高）→ 按（轴承, 阶次）分组统计复现次数。判定口径（2026-11 重新标定）：阈值 `max(ENV_FAULT_AMP_FLOOR=0.2, ENV_FAULT_REL=5.0 × 同测点跨机组中位数)`，同测点少于 3 个机组时只用绝对下限；**同一阶次复现 ≥2 次且幅值中位数 ≥ 阈值 → 警告**，只出现 1 次的大峰值最多「关注」；只有 1 条记录时需 ≥1.5×阈值才警告。（旧口径 `max(3.0, 5×中位)` 比实测最大包络幅值 0.46 还高，发电机轴承永远报不出来。）齿轮判读仍取 RMS/GE 最大的那条记录。**交叉排除**（`fault_freq_conflict`）：命中频率若与 1X/2X/3X 转频或齿轮啮合频率（±2%）重合、或只命中 1×（`weak`，证据不足）、或两只轴承分不清（`ambiguous`）→ 一律不升“警告”，最多“关注”，并在报告里写明“仅 1× 命中”“临近 1X 转频、需排除”。**判读依据可追溯**：诊断段末尾自动附 `（判读依据：数据 2026-06-11 07:04，fs 25600Hz，解调 1000–8000Hz，阈值 0.50）`，由 `report_evidence_text` 生成、`report_demod_band` 提供与实际计算同源的解调带。**黄金案例回归**：`tests/test_golden_cases.py` 把《齿轮啮合图谱经验.md》§6 里有频谱证据的案例（1.3/1.4/3.1/5.1/6.1 等）固化成合成谱用例，断言“GMF + 边带间隔 → 命中谁”，改判读逻辑时先跑它。
   - **齿轮**：同一条链上跑 `report_gear_scan`（取 RMS 最大那条记录，截 262144 点）→ 按机型 `gears` 逐级算 GMF，挑“谱上最明显的一级”（GMF 峰值/邻域中位），再用 `gear_sideband_verdict` 量边带间隔 → 命中轴转频 / GMF÷gcd / GMF÷planets / N×太阳轮。边带/主峰 ≥0.30 判「警告」、≥0.12 判「关注」，其余正常。结论写进 `agg[...]["gear"]` + `gear_lab`（`report_apply_faults`）。**齿轮结论可以单独把测点抬成关注/警告，不需要轴承也报警。**
   - **扫描只跑一次、两条路径共用**：`ReportDialog._go` 在选完模板之前统一调 `report_scan_faults(..., cache_path=<项目>\vib_scan_cache.json, progress=…)`，然后模板路径直接 `tpl_fill.fill`、内置版式用 `build_template_report(..., scan_faults=False)`（否则会重扫一遍，白等一倍时间）。扫描期间有 `_ScanProgress` 进度窗。

5. **选模板**：`profile_template :5292`（`项目档案.json` 的 `template.path`，失效回退 `backup`）；都没有就在 `数据\模板`、`模板`、`<项目>\模板`、程序目录里挑**最新 .docx**（`:5610-5624`）。

## 6. 已知坑与注意点

1. **`启动振动分析.bat` 是 GBK（实测 58 字节，内容纯 ASCII + GBK 编码的中文文件名）**。用 UTF-8 另存后 cmd 按 936 代码页读会找不到 `振动分析.py`，双击闪退。改这个文件必须用 GBK/ANSI 存。
2. **【已修复】`_bearing_dialog` 的“自定义倍数”曾必崩**：旧代码 `ok()` 里 `for _k,_v in v_cust.items()` 引用的 `v_cust` 只在 `_gear_dialog` 定义，轴承对话框没有这组控件 → 点「确定」抛 `NameError`，pythonw 下静默失败。
   - 修复：在 `_bearing_dialog` 补回 BPFI/BPFO/BSF/FTF 四个输入框（`:2640-2649`），并改为**逐项覆盖**（`mult = dict(mult); mult.update(_cust)`，`:2681-2683`）——旧写法 `mult = _cust` 会整体替换，导致没填的项也丢失；同时避免直接改动 `BEARING_LIB` 里的字典（那是全局表）。
   - 回归测试：`tests/test_bearing_dialog.py`（用 Tk 真实驱动对话框，验证库值/自定义/不污染全局表），运行 `python tests/test_bearing_dialog.py`。
3. **轴承/机型数据全部外置，代码里一个机型数字都没有**（2026-11 重构，之前是 `BEARING_LIB` + `GB_I1/I2/I3` 写死明阳，其它项目必然算偏）。
   - `数据\轴承库.json`：`{"bearings": {"轴承名": {"shaft": "H|M|S|L|P", "BPFI","BPFO","BSF","FTF"}}}`，132 条。同名整体覆盖、新名追加；`shaft` 非法、数字非法、无有效倍数只记 warning 不中断启动。示例见 `数据\轴承库.example.json`（明阳 14 条）。
   - `数据\机型库.json`：`{"machines": {"机型名": {"projects": ["项目名关键字"], "shafts": {"H":1.0,"M":…}, "gears": [{"name","teeth","shaft","sideband"}], "points": [["测点关键字", ["轴承名"]]]}}}`，17 个机型。**每个项目用自己的齿轮比**：`shafts` 是「该轴转频 ÷ 高速轴转频」，由文件名里的转速换算。
   - 生成工具：`tools\build_libs.py`（读现场两张表，一次性重建两个 JSON；`--dry-run` 只看统计）。**改倍数/齿数优先改 JSON，不要动源码。**
   - 项目没匹配到机型时：只认高速轴（`shaft:"H"` 的轴承仍准），其它轴不画；想支持就在 `机型库.json` 的 `projects` 里加项目名关键字。谱图里也可用轴承/齿轮对话框顶部的「机型」下拉临时选。
   - 回归测试：`tests\test_machine_lib.py`（42 项：结构、项目匹配、明阳口径不变、五峰对附件2 反算、自动标注、齿轮啮合、非法字段容错）、`tests\test_bearing_import.py`（13 项：结构 + 抽查 + 对原表全量反算 420 个频率）、`tests\test_bearing_lib.py`（14 项：加载器容错）。
   - 数据来源与优先级：运达 2.0MW（五峰）取《运达各类型机组振动档案库.xls》2000kW 页「南高齿FD2250Z」（附件2）；附件1《运达2.0MW轴承参数.xlsx》的 BPFO/BPFI 两列是反的、且用 1757rpm 当基准，只作核对，**以附件2 的绝对频率 ÷ 该轴转频重算**。其它 14 个机型取《C各机组振动诊断参数表-dd-3（20140103）.xls》，倍数按「第 9 列特征频率 ÷ 该页电机转频」归一成 `shaft:"H"`。
   - `数据\` 里的 xlsx/xls 仍然**不在运行时读**：只有 `tools\build_libs.py` 在生成 JSON 时读一次（需要 `xlrd`，已在 requirements 里）。改表不会自动生效，要重跑工具。
4. **滤波器 Nyquist 口径**：任何新滤波必须走 `design_band :472`（真实 `fs/2`）。历史上多处把 `fs/2.56` 当 Nyquist，导致截止频率偏大 1.28 倍、`Wn>=1` 时 scipy 抛 `ValueError`（“包络带通错误”弹窗）。`fs/2.56` 只用于**显示/分析上限**（`:394`、`:4199`）。
5. **改动计算口径必须同时 bump 版本号**：`VDI_VERSION=3 :292` 决定 SQLite 里的旧行是否重算，`DB_SCHEMA_VERSION=2 :69` 决定表结构。只改算法不改 `VDI_VERSION` → 老库照旧秒开、新算法不生效；库版本高于程序会直接抛“请升级程序”（`:718`）。
6. **中文显示**：matplotlib 只配了 `['SimHei','Microsoft YaHei']`（`:54`）且 `axes.unicode_minus=False`。**不要指定 `family="SimSun"`**：`findfont` 能解析到 `simsun.ttc`，但本机渲染出的是空字形——中文整段消失、只剩数字错位（2026-11 的“右上角齿轮判读像乱码”就是它）。新增文字一律跟随 rcParams；信息面板正文还用 `multialignment="left"` 明确左对齐。缺字体 → 方框。改了字体名要删 `~/.matplotlib/fontlist-*.json` 缓存。docx 侧用 `黑体`/`宋体`（`build_template_report :5876`、`tpl_fill` 不改字体）。
7. **性能**：单文件 8238 行 / 400KB，全函数平铺，没有模块拆分；`SpectrumWindow` 一个类 3400+ 行、60+ 方法。改一处务必全文搜同名局部变量（`v_*`、`_r`、`_p` 这类短名在多个 `ok()` 闭包里重复）。
8. **大目录/大数据**：一个 CSV 常在几 MB～几十 MB，全量重算走 8 线程（`:7203`）+ 进度窗，窗口期间 `grab_set` 且禁止关闭（`:7182`）。异常必须落到 `state["error"]` 并置 `finished`，否则进度窗永远停在最后一个数字（`:7188` 有注释）。读 CSV 用 `pd.read_csv` 全量，几万文件时这是主要瓶颈。
9. **线程纪律**：工作线程不得碰 Tk；自相关/瀑布都走“主线程取信号 + 线程算 + `after` 轮询”（`:3912-3969`）。SQLite 连接按线程各开各的（`:7227`）。
10. **路径与编码**：全部 JSON 用 `encoding="utf-8"`；源码首行 `# -*- coding: utf-8 -*-`，文件无 BOM。新增文件读写请显式给 encoding，Windows 默认 GBK 会读写失败。
11. 16 个无人调用的函数（`export_excel`、`build_report_docx`、`load_cache/save_cache`、`db_replace_all`、`butter_bandpass` 等）已删除；`trend_summary.json` 只读不写。出错但能继续的地方现在都走 `log_error()` 写到 `logs/vib_error.log`（超过 512KB 轮转成 `.1`），排查先看这个文件。
12. **`parse_filename` 失败是静默的**（返回空 dict → 文件被跳过）。文件名对不上时先看 `load_all_files` 结束后的“部分数据未计算”弹窗（`:7263`），或手动跑 `parse_filename` 验证。
